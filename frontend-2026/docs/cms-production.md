# Production editorial desk (custom CMS, no Strapi)
Deploy the static site from frontend-2026 and run the included Node service on the production host. /admin/ is served by the authenticated service, not by the old localStorage demo. No demo drafts are imported. Vercel previews do not write production data.

1. Use Node 24 on one persistent host. Create a private directory owned by the service user for SQLite (including WAL/SHM). Do not use ephemeral or shared network storage. Record and test an off-host backup and restore before launch. Use SQLite's online backup or VACUUM INTO; do not copy a live database file alone.
2. Register a company-owned GitHub OAuth app with the exact HTTPS callback https://YOUR-SITE/admin/callback. No repo scope is needed. Require staff to use MFA on their GitHub accounts. Set CMS_ORIGIN to the exact site origin without a trailing slash, CMS_DB to the absolute persistent database filename, CMS_GITHUB_CLIENT_ID and CMS_GITHUB_CLIENT_SECRET in the host secret store. Set CMS_EDITOR_IDS and CMS_PUBLISHER_IDS to comma-separated numeric GitHub user IDs (not usernames). Publishers also have editing access. Update allowlists and restart to revoke access. Never use the demo for private or real content.
3. Run node cms/server.mjs under a supervised service with restart enabled. It binds to 127.0.0.1:8788 by default; PORT and CMS_BIND are configurable. Terminate HTTPS on the same origin as the public site. Proxy /admin/ (including its assets, OAuth routes and API) and /api/cms/ to this service, retaining the full path. Redirect /admin to /admin/. Disable CDN caching for those paths and rate-limit login requests at the edge. Do not override Origin or cache private responses. Use one service instance (OAuth handshakes are in process memory).
4. With the API reachable, run npm ci, npm run build, npm test, then node scripts/prepare-production-cms.mjs. Deploy out/; the last command wires the public feeds and removes the demo. Do not deploy the repository root or route the contact API to the CMS. Purge any old news-config.js and recruit-config.js from the CDN.
5. On staging, log in as editor and publisher separately. Save a Japanese news draft and verify it is absent publicly. Publish and confirm TOP, news list and detail. Edit without publishing: old published copy must remain. Confirm EN can be saved/published independently. Publish then withdraw a job and check list/detail; withdrawn jobs keep their draft. Verify anonymous sessions cannot read the desk. Repeat smoke checks after the production switch using approved content. Send Chili the live /admin/ URL and confirm his allowed publishing account.
6. Rollback: restore the previous static output/config and routing, stop the new service, and preserve the private database. No existing Strapi database, form or public post is modified. If the old site has articles or jobs that must be retained, migrate approved records or keep the old feeds available before switching.
